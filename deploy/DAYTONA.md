# اجرا روی Daytona

---

## ⚠️ دو تنظیم که همه‌چیز به آن‌ها بند است

Daytona برای محیط توسعه و بارِ عامل‌های هوشمند ساخته شده، نه
میزبانیِ ۲۴ ساعتهٔ ربات. شدنی هست، ولی دو تنظیم باید درست باشد
وگرنه ربات می‌ایستد یا — بدتر — گنجینه از دست می‌رود.

### ۱) `auto-stop` باید **۰** باشد

پیش‌فرضش **۱۵ دقیقه** است: اگر ۱۵ دقیقه رویدادی در سندباکس نباشد،
خاموش می‌شود. ربات تلگرام که polling می‌کند، از دید Daytona
«رویداد سندباکس» نمی‌سازد — پس ربات شما هر ۱۵ دقیقه خاموش خواهد
شد.

```
--auto-stop 0     ← هرگز خودکار خاموش نشو
```

### ۲) 🔴 `auto-delete` هرگز **۰** نباشد

اینجا تلهٔ خطرناکی هست: **معنای صفر در این دو تنظیم وارونه است.**

| تنظیم | مقدار ۰ یعنی |
|---|---|
| `auto-stop` | هرگز خاموش نشو ✅ |
| `auto-delete` | **به‌محض خاموش شدن، پاک شو** 🔴 |

اگر `auto-delete 0` بگذارید، اولین باری که سندباکس بایستد،
**کل گنجینه پاک می‌شود** — پایگاه داده، اثر انگشت‌ها، همه.

در سند استقرار نوشتم و اینجا هم می‌نویسم: گنجینهٔ اثر انگشت
باارزش‌ترین چیز این پروژه است و بازسازی‌اش ناشدنی. فایل‌ها را
می‌شود دوباره گرفت؛ ماه‌ها یادگیریِ تصحیح‌های کاربران را نه.

**خبر خوب:** سیستم فایل در Daytona ماندگار است — با stop/start
پرونده‌ها، بسته‌های نصب‌شده و پایگاه داده سر جای خود می‌مانند.
تنها حافظه (RAM) پاک می‌شود. پس تا وقتی سندباکس **پاک یا بایگانی**
نشود، داده امن است.

## گام‌به‌گام

### ۰) توکن تازه

🔴 اگر هنوز نکرده‌اید: در @BotFather → `/mybots` → ربات →
`API Token` → `Revoke current token`.

توکن پیشین مدت‌ها در دو پروندهٔ متنی ساده بود. برداشتمش، ولی
برداشتن امنش نمی‌کند — تنها باطل کردن.

### ۱) ساختن سندباکس

در داشبورد یا با CLI. اگر CLI دارید:

```bash
daytona create --auto-stop 0 --auto-archive 0
```

اگر از داشبورد می‌سازید، پس از ساخت حتماً همین دو را بررسی کنید.
`auto-delete` را **دست نزنید** (پیش‌فرضش بی‌خطر است).

### ۲) پیش‌نیازها

```bash
sudo apt update
sudo apt install -y python3 python3-venv python3-pip ffmpeg
ffmpeg -version        # باید جواب بدهد
```

`ffmpeg` با pip نصب نمی‌شود و بی آن هیچ صوتی رمزگشایی نمی‌شود.

### ۳) بردنِ پروژه

پوشهٔ پروژه را بالا بفرستید (آپلود داشبورد، `git clone`، یا
`daytona` CLI).

**`.env` را از دستگاه خودتان نبرید** — روی سندباکس تازه بسازید.

### ۴) نصب

```bash
cd ~/hadis            # یا هر جا که گذاشتید
python3 -m venv .venv
.venv/bin/pip install --upgrade pip
.venv/bin/pip install -r requirements.txt
```

### ۵) پیکربندی

```bash
cp .env.example .env
nano .env
chmod 600 .env
```

پر کنید: `BOT_TOKEN` (توکنِ **تازه**)، `ADMIN_IDS`، `CHANNEL_ID`،
`CHANNEL_URL`، و شناسهٔ گروه‌ها.

### ۶) نخستین اجرا — دستی

```bash
.venv/bin/python main.py
```

باید پیام راه‌اندازی بدهد و بایستد. با Ctrl+C ببندید. اگر خطایی
هست، همین‌جا دیده می‌شود نه نیم‌شب.

### ۷) اجرای پایدار

سندباکس کانتینر است و **systemd ندارد**، پس `hadis.service` آنجا
به کار نمی‌آید. به جایش:

```bash
chmod +x deploy/run.sh
nohup ./deploy/run.sh > logs/runner.log 2>&1 &
```

`run.sh` نگهبان است: اگر ربات افتاد برش می‌خیزاند، با درنگِ
فزاینده تا اگر ایراد پایدار بود در چرخهٔ تند نیفتد.

دیدن گزارش:

```bash
tail -f logs/runner.log
tail -f logs/bot.log
```

بستن:

```bash
pkill -INT -f deploy/run.sh
```

## پس از راه‌اندازی

- **نمایه‌سازی دوباره** خودکار در پس‌زمینه آغاز می‌شود. تا پایانش
  جست‌وجو ناقص است.
- ربات باید در هر کانالی که به فهرست‌ها می‌افزایید **مدیر** باشد.
- ربات‌های تلگرام تاریخچهٔ کانال را نمی‌خوانند؛ تنها پستِ تازه.

## 🔴 پشتیبانِ بیرونی — اینجا مهم‌تر از سرور معمولی

پشتیبان شبانه ساعت ۳ در `backups/` گرفته می‌شود. ولی آن پشتیبان
**داخل همان سندباکس** است. اگر سندباکس پاک یا بایگانی شود، هر دو
با هم می‌روند.

هفته‌ای یک بار بیرون ببریدش:

```bash
# از دستگاه خودتان
daytona ssh <sandbox> -- tar czf - backups/ > hadis-backup-$(date +%F).tgz
```

یا ساده‌تر: `/backup` را در خود ربات بزنید تا فایل پشتیبان را در
تلگرام برایتان بفرستد. آن نسخه بیرون از سندباکس می‌ماند.

## اگر Daytona برایتان نساخت

سندباکس برای این کار ساخته نشده و ممکن است به دردسر بیفتید
(خاموشیِ ناخواسته، بایگانی شدن). یک VPS ساده — هتزنر، دیجیتال‌اوشن
— ماهی چند یورو است و برای ربات ۲۴ ساعته طبیعی‌تر.

برای آن حالت `deploy/hadis.service` و `deploy/README.md` آماده‌اند:
systemd خودش نگهبانی می‌کند و با بوتِ سرور بالا می‌آید.
